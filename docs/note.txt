FlaskYL - рабочая записка по проекту

Пишу это не как формальную пояснительную записку, а как обычную заметку для себя. Смысл файла простой: если через месяц открыть проект заново, быстро вспомнить, как он устроен и куда смотреть в первую очередь.

Что это за проект

Это Flask-приложение для управления VPN-сервисом.

По факту здесь есть три слоя

- обычный сайт с HTML-страницами;
- админка;
- REST API.

Сайт решает прикладную задачу: пользователь регистрируется, запрашивает тариф, получает подписку, добавляет устройства, а дальше сайт сам связывается с VPN-сервером и выдаёт или отзывает доступ.

Основной сценарий такой:

1. Пользователь регистрируется.
2. Выбирает тариф и оставляет заявку.
3. Админ одобряет заявку.
4. У пользователя появляется активная подписка.
5. Пользователь добавляет устройство.
6. Если включён автопровижининг, Flask идёт по SSH на VPN-сервер, создаёт Xray-клиента и возвращает готовую VLESS-ссылку.
7. Если подписка истекла, отозвана или закончился трафик, доступ на сервере тоже отзывается.

То есть это не просто витрина, а уже рабочая панель управления VPN.

Как я это собрал

Архитектура здесь монолитная. Я не делил проект на отдельный backend, отдельный frontend и отдельный API. Всё живёт в одном Flask'e. Для такого размера это нормально: быстрее разрабатывать, меньше лишней инфраструктуры и проще дебажить.

Картинка в голове должна быть такая:

- 'app.py' только запускает приложение;
- 'lowlands_vpn/__init__.py' собирает Flask app;
- 'models.py' хранит структуру данных;
- 'routes.py' отвечает за обычный сайт и админку;
- 'api.py' отвечает за REST API;
- 'services.py' хранит бизнес-логику подписок;
- 'vpn.py' связывает приложение с Xray-сервером;
- 'templates/' содержит HTML;
- 'scripts/' содержит утилиты и server-side helper scripts;
- 'migrations/' содержит Alembic-миграции.

Почему здесь есть REST API

REST API для проекта обязателен, поэтому я держу его как отдельный blueprint '/api'. Он не заменяет HTML-интерфейс, а существует рядом с ним.

Сайт и API работают поверх одних и тех же моделей и сервисов. Это важно: логика не дублируется в двух разных местах. Если действие есть и на сайте, и в API, оно должно упираться в одну и ту же бизнес-логику.

Как приложение стартует

'app.py' почти пустой. Он просто импортирует 'create_app()' и поднимает Flask.

Вся настоящая инициализация находится в 'lowlands_vpn/__init__.py'.

Что там происходит:

- создаётся Flask app;
- подтягивается конфиг из 'Config';
- инициализируются 'db', 'csrf', 'login_manager';
- регистрируются 'main_bp' и 'api_bp';
- подключается логирование;
- подключается CLI-команда 'flask make-admin';
- регистрируется обработчик CSRF-ошибок;
- вызывается 'init_database()'.

Главная функция здесь - 'create_app(test_config=None)'. Это точка сборки всего приложения.

Остальные функции в '__init__.py':

- 'register_cli_commands(app)' - добавляет CLI-команду 'make-admin', чтобы можно было выдать админские права по email;
- 'configure_logging(app)' - настраивает базовое логирование и предупреждает, если 'SECRET_KEY' остался дефолтным;
- 'register_error_handlers(app)' - красиво обрабатывает CSRF-ошибки и отдаёт отдельный шаблон.

Конфиг

'lowlands_vpn/config.py' - это центральное место для runtime-настроек.

Важные вспомогательные функции:

- 'get_env_bool(name, default)' - безопасно читает булевы значения из env;
- 'get_env_int(name, default)' - то же самое для чисел;
- 'normalize_database_uri(uri)' - приводит строку подключения к базе к удобному виду.

Класс 'Config' хранит всё, что нужно приложению:

- 'SECRET_KEY';
- 'DATABASE_URL';
- флаги debug и cookie;
- 'BOOTSTRAP_SCHEMA_ON_STARTUP';
- SSH-настройки для VPN-сервера;
- пути до server-side helper scripts;
- параметры для локальной сборки VLESS-ссылки.

Если приложение ведёт себя не так, как ожидается, сначала почти всегда стоит проверить именно этот файл и фактические env-переменные.

Расширения

'lowlands_vpn/extensions.py' предельно простой. Там лежат общие объекты:

- 'db';
- 'csrf';
- 'login_manager'.

Смысл в том, чтобы не создавать их внутри каждого модуля, а один раз объявить и потом инициализировать внутри 'create_app()'.

База и её инициализация

'lowlands_vpn/database.py' отвечает за стартовое приведение базы в рабочее состояние.

Главные функции:

- 'init_database(instance_path)' - общая точка входа;
- 'schema_exists()' - проверяет, есть ли основные таблицы;
- 'apply_additive_schema_patches()' - аккуратно добавляет недостающие колонки в старых схемах;
- 'seed_tariffs()' - синхронизирует таблицу тарифов с 'PLANS'.

Здесь есть немного переходной логики из старых этапов проекта. Исторически база была на SQLite, потом проект переехал на PostgreSQL + Alembic. Поэтому в коде всё ещё остался bootstrap-режим и additive patches. Это не идеально, но работает и не мешает.

Бизнес-логика подписок

'lowlands_vpn/services.py' - это компактный файл с логикой, которую не хотелось размазывать по route-ам.

Главные вещи:

- 'SUBSCRIPTION_REQUEST_TYPE' - строковая константа для invoice-заявок;
- 'get_subscription_revoke_reason(subscription)' - формирует понятную причину отзыва устройства;
- 'revoke_subscription_devices(subscription)' - отзывает все устройства подписки;
- 'sync_user_subscriptions(user)' - синхронизирует статусы подписок пользователя и при необходимости автоотзывает устройства;
- 'get_current_subscription(user)' - возвращает текущую релевантную подписку;
- 'get_pending_subscription_request(user)' - ищет последнюю необработанную заявку;
- 'create_subscription_request(user, tariff)' - создаёт invoice-заявку на тариф;
- 'approve_subscription_request(invoice, reviewer_id)' - превращает заявку в активную подписку или продлевает существующую.

Здесь же находится важная логика: если подписка перестала быть активной, устройства надо отзывать не только в базе, но и на VPN-сервере.

Интеграция с VPN

'lowlands_vpn/vpn.py' - один из самых важных файлов проекта.

Он отвечает за то, чтобы Flask не лазил напрямую в Xray-конфиг, а работал через серверные helper scripts по SSH.

Ключевые сущности и функции:

- 'VpnProvisioningError' - общее исключение для VPN-ошибок;
- 'RemoteCommandResult' - результат remote-команды с JSON payload, stdout и stderr;
- 'is_vpn_auto_provisioning_enabled()' - вообще настроен ли VPN runtime;
- 'can_build_vless_link_locally()' - хватает ли локальных параметров для сборки ссылки без сервера;
- 'ensure_device_vpn_identity(device)' - гарантирует, что у устройства есть UUID и email;
- 'get_device_link_name(device)' - человекочитаемое имя для VLESS-ссылки;
- '_build_vless_link_locally(device)' - собирает 'vless://...' локально;
- '_build_vless_link_remotely(device)' - просит сервер собрать ссылку;
- 'build_vless_link(device)' - выбирает нужный способ;
- 'provision_device(device)' - выдаёт доступ на сервере и сохраняет ссылку;
- 'revoke_device_on_server(device)' - отзывает доступ на сервере;
- 'remove_server_vless_client_by_uuid(client_uuid)' - удаляет серверного клиента напрямую по UUID;
- 'run_remote_command(script_path, *script_args)' - низкоуровневый SSH-вызов;
- 'run_remote_json_command(script_path, *script_args)' - то же самое, но ждёт JSON;
- '_looks_like_existing_client_error(error_message)' - помогает не падать на повторной выдаче;
- 'list_server_vless_clients()' - читает live-клиентов с сервера.

Практически вся магия VPN живёт здесь. Если выдача ссылки сломалась, смотреть в первую очередь надо в этот файл и в server-side scripts.

Обычные маршруты и админка

Пользовательские route-ы:

Админские route-ы:

- 'admin_users()' - список пользователей;

Логика у 'routes.py' в целом несложная, но файл разросся. Если когда-то захочу упрощать проект дальше, первым делом буду делить его на 'auth.py', 'dashboard.py', 'admin.py'.

REST API

'lowlands_vpn/api.py' - отдельный blueprint с префиксом '/api'.

Я оставил его на обычном Flask 'Blueprint', без лишних обёрток. Для текущего размера проекта это проще и честнее, чем городить отдельный слой ради самого факта.

Внутри 'api.py' есть три типа кода.

Первый - общие helper-функции:

- 'json_success()' - единый формат успешного ответа;
- 'json_error()' - единый формат ошибки;
- 'get_json_payload()' - безопасно читает JSON-запрос.

Второй - декораторы доступа:

- 'api_login_required';
- 'api_admin_required'.

Третий - сериализаторы:

- 'serialize_datetime';
- 'serialize_tariff';
- 'serialize_subscription';
- 'serialize_device';
- 'serialize_invoice';
- 'serialize_user'.

Это нужно, чтобы API не лепил JSON вручную в каждой ручке.

Текущие endpoint-ы API:

- 'GET /api' - краткая справка по API;
- 'GET /api/tariffs' - список активных тарифов;
- 'POST /api/auth/login' - логин по email и паролю;
- 'POST /api/auth/logout' - завершение сессии;
- 'GET /api/auth/me' - текущий пользователь, подписка и pending-заявка;
- 'GET /api/invoices' - список invoice-записей пользователя;
- 'GET /api/subscriptions/current' - текущая подписка;
- 'POST /api/subscriptions/request' - создать заявку на тариф;
- 'GET /api/devices' - список устройств пользователя;
- 'POST /api/devices' - создать устройство;
- 'POST /api/devices/<device_id>/revoke' - отозвать устройство;
- 'GET /api/admin/overview' - базовая сводка для админа;
- 'GET /api/admin/users' - пользователи;
- 'GET /api/admin/server-vless-clients' - live VLESS-клиенты на сервере.

API использует ту же сессию Flask-Login, что и обычный сайт. Это не отдельная токенная схема.

Миграции

В 'migrations/' лежит Alembic.

Сейчас важны две миграции:

- '20260408_0001_initial_schema.py' - базовая схема;

Скрипты

Что здесь есть:

- 'export-vpn-server-state.sh' - снять состояние VPN-сервера для backup/анализа;
- 'migrate-sqlite-to-postgres.py' - перенос данных со старой SQLite на Postgres;
- 'setup-restricted-vpn-ssh.sh' - настройка ограниченного SSH-доступа до VPN helper scripts;
- 'start-postgres-tunnel.sh' - временный SSH-туннель до Postgres, если нужен;
- 'xray-add-client.sh' - добавить клиента в Xray;
- 'xray-remove-client.sh' - удалить клиента из Xray;
- 'xray-build-vless-link.sh' - собрать VLESS-ссылку;
- 'xray-list-clients.sh' - получить live-список клиентов;
- 'xray-ssh-dispatch.py' - forced-command dispatcher для restricted SSH;
- 'xray.env.example' - пример env-файла для серверных скриптов.

Если коротко, Flask сам не редактирует 'config.json' на VPN-сервере. Он вызывает эти скрипты по SSH.

Тесты

В 'tests/' сейчас основной файл - 'test_core_flows.py'.

Название историческое. По факту там уже не только “неплатёжные” сценарии, а почти весь regression suite по основным функциям проекта.

Что там покрыто:

- регистрация и логин;
- доступность страниц;
- админка и права доступа;
- заявки на подписки;
- одобрение подписок;
- устройства;
- автоотзыв;
- VPN sync;
- REST API.

'tests/conftest.py' поднимает тестовое окружение и изолирует тесты от живого runtime.

Как идёт основной поток данных

Чтобы быстро восстановить картину, полезно держать в голове несколько цепочек.

Регистрация:

'register()' -> создаётся 'User' -> запись уходит в базу.

Заявка на тариф:

'request_subscription()' или 'POST /api/subscriptions/request' -> 'create_subscription_request()' -> создаётся 'Invoice' типа 'subscription_request'.

Одобрение админом:

админ открывает карточку пользователя -> жмёт approve -> 'approve_subscription_request()' -> создаётся или продлевается 'Subscription'.

Добавление устройства:

'create_device()' или 'POST /api/devices' -> создаётся 'Device' -> если включён VPN runtime, вызывается 'provision_device()' -> на сервере создаётся Xray-клиент -> ссылка сохраняется в 'device.vpn_link'.

Отзыв:

если пользователь отзывает устройство сам или подписка становится неактивной -> 'revoke_device_on_server()' -> 'device.mark_revoked()'.

Сверка с live Xray:

админ вызывает sync -> 'synchronize_vpn_runtime_state()' -> Flask сравнивает локальные устройства и реальных клиентов на сервере -> подтягивает ссылки, удаляет хвосты, помечает пропавшие устройства как 'failed'.

На что смотреть при проблемах

Если ломается авторизация:

- 'forms.py'
- 'routes.py' ('login', 'register')
- 'models.py' ('set_password', 'check_password')

Если не создаётся подписка:

- 'services.py'
- 'approve_subscription_request()'
- 'Subscription' в 'models.py'

Если не выдаётся VPN:

- 'vpn.py'
- server-side scripts в 'scripts/'
- env-настройки в 'config.py'

Если админка показывает не то, что есть на сервере:

- 'synchronize_vpn_runtime_state()'
- 'list_server_vless_clients()'
- 'xray-list-clients.sh'

Если API отдаёт странный JSON:

- 'api.py'
- сериализаторы в этом же файле

Что в проекте главное

Если совсем коротко, проект держится на трёх файлах:

- 'models.py' - что вообще хранится;
- 'services.py' - как живут подписки;
- 'vpn.py' - как сайт связан с Xray.

Всё остальное - это уже слой интерфейса:

- 'routes.py' для HTML;
- 'api.py' для JSON;
- 'templates/' для отображения.

Краткий итог

Сейчас проект - это монолитный Flask-сервис с HTML-интерфейсом, админкой, обязательным REST API и интеграцией с Xray по SSH.

Он уже умеет:

- вести пользователей;
- хранить тарифы;
- активировать и продлевать подписки;
- управлять устройствами;
- выдавать и отзывать VPN-доступ;
- показывать live-состояние серверных клиентов;
- отдавать те же данные через API.

Если открывать проект после паузы, я бы смотрел в таком порядке:

2. 'lowlands_vpn/models.py'
3. 'lowlands_vpn/services.py'
4. 'lowlands_vpn/vpn.py'
5. 'lowlands_vpn/routes.py'
6. 'lowlands_vpn/api.py'

Этого уже достаточно, чтобы снова войти в контекст и дальше копать детали по месту.
